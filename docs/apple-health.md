# Apple Health

Односторонний перенос питания и веса через Apple «Команды» на одном iPhone.
Команда запускается вручную; HealthKit работает на устройстве с разрешения
пользователя. Команда опубликована ссылкой iCloud и ставится по ней; ключ
пользователь вставляет сам, затем проверяет первый показатель на устройстве.
Ручная сборка сохранена как резервный путь.

## Подключение

1. Обновите бот и веб-сервер по [инструкции развёртывания](miniapp.md).
   Нужны зависимости `.[miniapp]`, публичный HTTPS-сервер и `MINIAPP_URL` в боте.
   Используется существующий домен и порт Mini App, дополнительные службы не нужны.
2. В личном чате откройте **Settings → Apple Health → Подключить Apple Health**.
   Там же есть кнопка **Пошаговая инструкция для iPhone**.
   Можно также отправить `/health connect`. Ключ показывается один раз.
   По умолчанию экспорт начинается с начала текущего дня в часовом поясе дневника.
   `/health connect 2026-09-01` включает историю с указанного дня без верхней границы.
   `/health connect 2026-09-01 2026-09-30` задаёт закрытый период: записи вне него
   не выдаются, поэтому историю можно переносить частями. Ротация ключа без дат
   сохраняет обе границы; одна дата снова открывает экспорт новым записям.
3. Откройте ссылку из ответа бота и поставьте команду на iPhone. Инструкция
   поставляется с приложением: [`apple-health.html`](../kcaloriebot/static/apple-health.html)
   (публичный адрес `/static/apple-health.html`) — установка по ссылке iCloud,
   вставка ключа, первый запуск, разбор ошибок и восстановление. Ручная сборка
   вынесена в [`apple-health-manual.html`](../kcaloriebot/static/apple-health-manual.html)
   (`/static/apple-health-manual.html`): словарик, мини-курс по «Командам», карта
   готовой команды, 29 шагов и проверочный список. Веб-процесс читает статические
   файлы при старте, поэтому после правки страниц его нужно перезапустить.

   Ссылка iCloud в инструкции ведёт на команду с **зашитым адресом этого
   развёртывания** в двух действиях URL. Своё развёртывание: либо опубликуйте
   собственную команду и замените ссылку в `apple-health.html`, либо оставьте как
   есть — инструкция отдельным шагом требует сверить адрес с тем, что выдал бот,
   и заменить его. Ключа в опубликованной команде нет и быть не должно: он лежит
   внутри копии пользователя, поэтому пересылать свою команду нельзя.
4. Проверьте первый показатель в Health, затем запустите оставшийся перенос.

Обе границы — целые локальные дни: начало включительно, конец включительно
(в базе `end_utc` — локальная полночь следующего дня, NULL — без ограничения).
Уже подтверждённые показатели не выдаются повторно при смене периода, поэтому
перенос частями не создаёт дублей.

Команды `/health`, `/health disconnect`, `/health saved КВИТАНЦИЯ`,
`/health retry КВИТАНЦИЯ` и `/health corrected ID ВЕРСИЯ` показывают состояние,
отзывают ключ и позволяют подтвердить ручное восстановление. Бот выдаёт конкретные
команды с аргументами при незавершённой записи или изменении данных.
Выполняйте восстановление только после остановки команды на iPhone.

## Развёртывание и миграция

Схема SQLite 6 → 7 добавляет `health_connections` и `health_samples` без изменения
дневника. Схема 7 → 8 добавляет `health_connections.end_utc` — верхнюю границу
периода; NULL означает «без ограничения», то есть прежнее поведение. Перед
обновлением сделайте резервную копию и остановите оба процесса, затем запустите
бот и web с одинаковой версией кода. Используйте существующий порядок обновления
проекта. Старый код не принимает схему 8; откат требует предыдущей версии кода
и резервной копии базы.

Проверьте `GET /static/apple-health.html` и `GET /static/apple-health-manual.html`
(200), а также `POST /health/v1/next` без авторизации (401).
Если на `/health/v1/*` приходит HTML вместо JSON, отвечает не приложение:
веб-процесс лежит или Nginx проксирует не туда. Диагноз — в логе Nginx
(`connect() failed (111: Connection refused) ... upstream:` с адресом из
`proxy_pass`) и в `journalctl -u kcaloriebot-web`. Проверять приложение нужно
в обход Nginx: `curl -i http://127.0.0.1:<порт из proxy_pass>/health/v1/status`
должен отдать JSON с 401. Существующий Nginx `location /` уже проксирует новые адреса.
Не записывайте заголовок Authorization в логи. Ключ нельзя передавать в URL.
Ответы API используют `Cache-Control: no-store`.

## API v1

Все запросы используют `Authorization: Bearer <ключ из /health connect>`.
Это отдельный случайный ключ на пользователя, не токен Telegram-бота и не initData.
В базе хранится только SHA-256 ключа. Ротация и отзыв не удаляют квитанции и
незавершённый перенос. Ключ не даёт доступа к `/api/*` или редактированию дневника.
При ротации без даты сохраняется прежняя нижняя граница экспорта.

| Запрос | Тело | Результат |
| --- | --- | --- |
| `GET /health/v1/status` | нет | Состояние без резервирования показателя |
| `POST /health/v1/next` | `{}` | Резервирует один новый показатель |
| `POST /health/v1/ack` | `{"receipt":"…"}` | Подтверждает его запись в Health |

POST требует `Content-Type: application/json`. Параметры URL не поддерживаются.
Пустое тело равнозначно `{}`: Apple «Команды» не отправляют тело для запроса
с телом JSON без полей, поэтому `next` обязан принимать и такой запрос.
Невалидный/отозванный ключ: 401, неверный JSON: 400, чужая/устаревшая квитанция: 409.
Ошибка возвращает только `error`, без `status`: клиент, который читает `status`
вслед за ошибкой, получит пустое значение, а не сообщение об ошибке.

Пример ответа `next` (числа в `value` — уже итог за порцию, не за 100 г):

```json
{
  "status": "sample",
  "sample": {
    "id": "food:42:calories",
    "type": "calories",
    "value": 250.5,
    "unit": "kcal",
    "date": "2026-09-12T09:30:00+00:00",
    "epoch": 1789205400
  },
  "receipt": "random-receipt",
  "remaining": 4,
  "issues": [],
  "issue_count": 0,
  "confirmed": 0
}
```

Типы: `calories` → Dietary Energy (kcal), `protein` → Protein (g), `fat` →
Total Fat (g), `carbs` → Carbohydrates (g), `weight` → Weight (kg).
Неизвестные значения пропускаются, нулевые экспортируются. Будущие записи
не выдаются до наступления их времени. Дата передаётся как абсолютное UTC-время.

Состояния: `sample` разрешает одну запись; `review` означает незавершённую выдачу;
`changed` требует ручной сверки ранее подтверждённых значений; `done` означает
отсутствие новых данных. `ready` встречается только в `status`: данные доступны,
но ещё не зарезервированы, записывать их нельзя. `remaining` считает новые
показатели до резервирования; `confirmed` — квитанции, включая вручную сверенные
удаления. `issues` содержит максимум 10 изменений, `issue_count` — их общее число.

`ack` возвращает `{"status":"acknowledged"}`; повтор с той же квитанцией безопасен.
Записывать Health разрешено только при точном `status == sample`; любой другой
ответ, неизвестный тип и ошибка должны остановить команду до подтверждения.

## Границы синхронизации

Одновременная фиксация SQLite и HealthKit невозможна. Поэтому незавершённый
показатель никогда автоматически не выдаётся повторно. Сервер не может проверить,
что iPhone действительно записал данные: после сбоя пользователь сверяет конкретный
показатель и подтверждает наличие либо разрешает повтор. Одновременные запросы
сериализуются; только первый получает `sample`, остальные — `review`.

После исправления или удаления подтверждённого показателя экспорт останавливается:
старое и новое значения показываются в `/health`. Пользователь исправляет Health
вручную, затем подтверждает актуальную версию. Изменения неизвестных БЖУ в известные
значения становятся новыми показателями. Название блюда, размер порции и цели сами
по себе не экспортируются; изменения названия без изменения КБЖУ не создают конфликт.
Даже изменение старой записи за пределами начальной даты обнаруживается, если она
уже была перенесена. Изменение во время незавершённого переноса сверяется после ack.

Одна история переноса предназначена для одной базы Apple Health. Очистка Health
или перенос на устройство с пустой базой не сбрасывает серверные квитанции.
Автоматического повторного импорта подтверждённых данных и двусторонней
синхронизации в этой версии нет. Данные Health не отправляются серверу.

Проверка очереди читает показатели и квитанции пользователя; стоимость одного
запроса растёт с историей. Это реализация для личного дневника, без фонового
массового импорта. Квитанции хранятся без срока давности для защиты от повторов.
